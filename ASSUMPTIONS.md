# Assumptions

This document records explicit ambiguities and provisional assumptions for the research implementation. None of these choices should be silently inferred or treated as part of the source protocol without confirmation.

1. **Dataset availability:** CICIoT2023 will be acquired manually in a later phase; this task does not download or vendor any dataset files.
2. **Dataset location:** Raw files will be placed under `data/raw/`, and derived artifacts will be written under `data/processed/`.
3. **Target labels:** The implementation will use the eight classes specified in `PAPER_SPEC.md`, but the exact mapping from each original CICIoT2023 attack label to those classes must be established from the source protocol.
4. **Project-level class mapping:** The paper specifies an eight-class setup, but no authoritative 34-to-8 table was found. `Backdoor_Malware` (663 rows) and `VulnerabilityScan` (7,127 rows) could not be assigned to a target class and are quarantined rather than silently mapped.
5. **Input shape:** The model receives 46 features, but the sequence/channel arrangement required by Conv1D and the CNN-to-Transformer reshaping or tokenization are not specified.
6. **Splits:** The research paper used an 80/20 train/test evaluation split (processed via Spark) without specifying a separate hold-out validation partition. As an explicit implementation adaptation, this repository adopts a 70/15/15 train/validation/test stratified split by default in `config.yaml`. This provides a dedicated validation partition for model checkpointing and early stopping while keeping the test partition untouched for final unbiased evaluation.
7. **Normalization:** MinMax parameters will be fitted on training data only and reused for validation, test, and inference data. The feature range and behavior for values outside the training range are not specified.
8. **CNN details:** The third MaxPooling1D pool size, convolution padding/stride, and other unlisted layer options are unspecified.
9. **Transformer dimensions:** The specification gives 3 attention heads and embedding dimension 8. Standard multi-head attention often requires the embedding dimension to be divisible by the head count, so the source implementation must clarify how these values are reconciled.
10. **Transformer details:** Feed-forward dimensions, normalization order, positional information, CNN-to-Transformer interface, and the location of the stated post-attention dropout are unspecified.
11. **Activations:** CNN activations are specified as SeLU, but the Transformer feed-forward activation is ambiguous between SeLU and GELU; the source specification must decide this.
12. **Transformer facts explicitly specified by the paper:** The Transformer has an encoder, multi-head self-attention, 3 attention heads, an embedding-dimension value of 8, post-attention dropout `0.05`, residual or skip connections, Layer Normalization, and a feed-forward network.
13. **Transformer details not specified by the paper:** The paper does not define whether `8` is the total model/embedding width or the width of each attention head. It also does not define tokenization, the CNN-to-Transformer interface, sequence length, head-width allocation, projection layers, positional information, feed-forward dimensions, normalization order, or the feed-forward activation.
14. **Interpretation A, total model width:** If `8` means the total Transformer model width, the Transformer input would have shape `(batch, tokens, 8)`. Three heads are still technically possible, but an implementation must explicitly choose unequal head widths, framework-specific projections, or another nonstandard allocation because equal-width heads would require a non-integer width of `8 / 3`. This interpretation stays closest to the phrase embedding dimension but introduces attention-configuration risk.
15. **Interpretation B, per-head width:** If `8` means the dimension used by each head, 3 heads produce an internal concatenated attention width of `3 * 8 = 24`. A framework can accept token embeddings with width 8 and use per-head projections of width 8, or it can expose a 24-dimensional concatenated representation before an output projection. This interpretation is technically straightforward but assumes that the paper's embedding dimension refers to head width.
16. **CNN-to-Transformer bridge:** The implemented CNN emits `(batch, 64)`. The proposed reshape `(batch, 64) -> (batch, 8, 8)` is mathematically valid because `64 = 8 * 8`, preserves all values, and creates 8 tokens of width 8. It is consistent with the paper's stated numbers, but the paper does not explicitly state this tokenization or reshape; it is an implementation assumption. It does not by itself resolve whether the 8-wide tokens are total model width or per-head width.
17. **Bridge risks and tradeoffs:** The reshape is parameter-free and minimally invasive, but it imposes an arbitrary ordering and token boundary on the flattened CNN features. Interpretation A risks a nonstandard or framework-dependent 3-head allocation. Interpretation B is easier to implement with standard per-head projections, but may not match the paper if its 8 refers to total model width. A learned projection could address width mismatches, but would add an architecture detail not stated by the paper.
18. **Recommended implementation assumption:** Use Interpretation B with the `(batch, 8, 8)` reshape, treating 8 as the per-head attention width and using 3 heads with explicit framework parameters. This is the smallest technically valid and reproducible bridge that preserves the CNN output without adding a learned projection. It is not explicitly stated by the paper and must be reported as an implementation assumption.
19. **Transformer feed-forward implementation:** The paper specifies a feed-forward network but does not specify its hidden width or activation. The encoder uses a minimal two-layer pointwise FFN, `Dense(8, SeLU)` followed by `Dense(8)`, with no additional FFN dropout; this is an implementation assumption.
20. **Classifier aggregation:** The paper does not specify how the Transformer output is reduced before classification. The classifier uses parameter-free `GlobalAveragePooling1D`, preserving the width-8 representation and avoiding the larger parameter count of flattening; this is an implementation assumption.
21. **Regularization and optimization:** L2 regularization is specified as `0.001` for the dense CNN layers and dropout as `0.05`, but the regularization scope, Adam options, checkpoint selection, and early stopping are unspecified.
22. **Evaluation:** Accuracy, precision, recall, F1-score, confusion matrix, and per-class metrics are required. The averaging method for aggregate metrics and the exact reporting protocol are unspecified.
23. **Baselines:** MLP and XGBoost are required baselines, but their architecture, hyperparameters, and tuning protocol are unspecified.
24: **Reference results:** The paper accuracies are approximate reference values, not guaranteed targets. The implementation must report its own results without presenting them as reproduced values unless experimentally obtained.
25. **Reproducibility:** A default random seed of `42` is provided as a placeholder in `config.yaml`; it is not evidence of the source study's seed.
26. **Environment:** Python and TensorFlow / Keras are adopted for model training and preprocessing shard streaming.
27. **Repository policy:** Empty directories are created now to establish ownership boundaries. No implementation, notebook, checkpoint, or dataset artifact is included in this phase.
29. **Development mode sampling strategy and ordering bias:** In development mode (`mode: development`), the pipeline processes raw CSV chunks in order and selects the first `N` examples (default 100) per canonical class encountered. Once all 8 target classes satisfy this quota, chunk streaming terminates early (scanning ~400k rows instead of ~9 million rows), keeping development processing fast (<10 seconds) and memory-efficient. However, because network traffic in CICIoT2023 is generated chronologically during simulation runs, selecting the earliest encountered flows introduces an ordering bias (flows are clustered in time and originated from the first scanned file, with lower feature variance than a globally dispersed sample). This strategy is an intentional engineering tradeoff for rapid pipeline and integration testing; it must not be used for final model evaluation or benchmarking.
30. **Training loss function:** Sparse Categorical Crossentropy (`sparse_categorical_crossentropy`) is adopted to match the 8 integer target class IDs (0..7) yielded by `dataset.py`.
31. **Training hyperparameters:** Training uses Adam optimizer with learning rate `0.00005`, batch size `1024`, and `50` target epochs as specified in `PAPER_SPEC.md`.
32. **Model Checkpointing & Logging:** The best model weights (monitored via `val_loss`) and final model weights are saved under `checkpoints/cnn_transformer/`. Training history, CSV log, and run metadata are saved under `experiments/results/cnn_transformer/`.
33. **EarlyStopping Callback:** EarlyStopping is available as an optional engineering convenience (`--early-stopping`), disabled by default so that full 50-epoch paper-style training runs remain directly accessible.
